NextToolbar needs no configuration to work. This page lists what you *can* configure, in the component and in `next.config`.

## Props

```tsx
<NextToolbar theme="system" />
```

| Prop | Type | Default | Description |
|---|---|---|---|
| `theme` | `'system' \| 'light' \| 'dark'` | `'system'` | Initial theme. `system` follows the OS preference. The theme button in the toolbar overrides it and remembers the choice per browser. |
| `securityCheck` | `boolean` | `true` | Check your Next.js version against GitHub's security advisories. See [Security](./security). |

The package also exports the types `NextToolbarProps` and `Theme`.

## `next.config` options

| Option | Recommended | Why |
|---|---|---|
| `experimental.requestInsights` | `true` (Next 16.3+) | Unlocks server timing, fetches with cache outcome, server errors, exact route patterns, the no-store render-mode correction and the profiler. |
| `devIndicators` | `{ position: 'top-right' }` or `false` | Next's indicator sits bottom-left by default, on top of the toolbar's logo. |

```ts title="next.config.ts"
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  devIndicators: { position: 'top-right' },
  experimental: { requestInsights: true },
}

export default nextConfig
```

<Callout type="note">
  `requestInsights` only exists from Next 16.3. On older versions TypeScript flags it as an unknown option in `next.config.ts`, so only add it on 16.3+.
</Callout>

## `basePath` and `assetPrefix`

Both work without extra configuration:

- The toolbar finds the dev server's socket the same way Next's own client does: from the path of Next's scripts (everything before `/_next/`). That covers `basePath`, and `assetPrefix` including a CDN URL.
- Next writes `basePath` into the toolbar's code at build time (`process.env.__NEXT_ROUTER_BASEPATH`), so it can match URLs that include it (`/docs/blog/hello`) with the paths Next reports without it (`/blog/hello`).

## Persisted preferences

The toolbar stores two small preferences in the browser's `localStorage`, per origin:

| Key | Values | Set by |
|---|---|---|
| `next-toolbar:collapsed` | `'1'` or `'0'` | Minimizing / expanding the toolbar |
| `next-toolbar:theme` | `'system'`, `'light'`, `'dark'` | The theme button |
| `next-toolbar:seen` | JSON list of segment names | Opening a segment that has the **new** badge |

Clear them to go back to the defaults. If `localStorage` is unavailable (private mode, blocked storage), the toolbar still works and simply doesn't remember.

## Server route

Optional. `@angelitolm/next-toolbar/server` exports two route handlers; mount them at `/api/next-toolbar`:

```ts title="app/api/next-toolbar/route.ts"
export { GET, POST } from '@angelitolm/next-toolbar/server'
```

| Method | Does |
|---|---|
| `GET` | Returns the Server Action names, read from Next's `server-reference-manifest.json` files in `.next`. |
| `POST` | Runs `revalidatePath` or `revalidateTag` with what the toolbar sends. |

- Both answer **404 outside `next dev`**, so deploying the file is harmless (unless you [opt in on a staging server](#staging-self-hosted-qa)).
- They also answer 404 unless the request carries the `x-next-toolbar` header. Browsers only send a custom header to another origin after a CORS preflight, which this route never approves, so another site open in your browser can't call it.
- The path is fixed. If a `middleware`/`proxy` guards `/api`, let `/api/next-toolbar` through in development.
- It reads the manifests from `.next` in the directory `next dev` runs in: with a custom `distDir`, action names won't be found (revalidating still works).

## Error boundary

Not a toolbar option, but worth repeating: add `app/error.tsx` so a render error doesn't take the root layout, and the toolbar, down with it. See [Getting started](./getting-started#4-keep-it-on-screen-when-a-page-crashes).

## Demo component

`NextToolbarDemo` renders the same toolbar from data you pass in, in any environment, production included. It's what powers the [live demo](./demo); use it for documentation, screenshots or showcases, not in your app.

```tsx title="app/showcase/page.tsx"
'use client'
import { NextToolbarDemo } from '@angelitolm/next-toolbar/demo'

export default function Showcase() {
  return <NextToolbarDemo pathname="/blog/hello" params={{ slug: 'hello' }} status={200} timingMs={42} isStatic />
}
```

| Prop | Description |
|---|---|
| `pathname`, `params` | The simulated page |
| `status`, `timingMs`, `via` | HTTP status and TTFB (`'document'`) or navigation time (`'rsc'`) |
| `isStatic` | What Next's dev data says: `true`, `false`, or omitted for "Rendering…" |
| `insights` | Simulated request insights (types `Insight`, `InsightFetch`, `InsightSpan` are exported) |
| `clientErrors` | Client errors with `message` and optional `stack` |
| `nextVersion`, `theme` | Defaults: `'16.3.6'` and `'system'` |

## Production

There is nothing to switch off. In a production build the toolbar renders `null`, makes no request and opens no connection. Its code sits in a separate chunk that pages never load for your visitors.

## Staging (self-hosted QA)

NextToolbar is a development tool. **It does not belong in a production environment**, and nothing in the package turns it on there by itself.

A staging server used for specific QA testing is the one exception, and it is **a decision your development team makes on purpose**: the toolbar stays off until someone sets the secret below on that server. Do it only on staging, only for the time QA needs it, and never on the environment your users reach.

<Callout type="warning" title="Never in production">
  Do not set `NEXT_TOOLBAR_SECRET` in production, not even temporarily to debug. With the server route mounted, whoever holds the secret can list your Server Actions and revalidate your cache.
</Callout>

To enable it on a self-hosted staging server (`next build` + `next start`):

1. Mount the [server route](#server-route): it is what decides who gets in.
2. Set a secret of at least 16 characters on the server:

   ```bash
   NEXT_TOOLBAR_SECRET=a-long-random-string
   ```

3. In the browser that should see the toolbar, set the same value as the `next-toolbar` cookie (once, from the DevTools console):

   ```js
   document.cookie = 'next-toolbar=a-long-random-string; path=/; max-age=2592000; samesite=strict'
   ```

4. Reload the page. The toolbar appears for that browser only.

### What QA sees on staging

A production build has no Next dev server, so everything that comes from it is missing. The rest works as in development.

| Works | Missing, and why |
|---|---|
| HTTP status, TTFB and client navigation time | **Render mode** (Static / Dynamic): Next only sends it over the dev server's HMR socket |
| **Cached fetches**: every fetch in Next's data cache, newest first, with HTTP status, freshness, tags, response headers and revalidate buttons ([details](./fetch-cache#on-a-staging-server)) | **Fetches per request**, their time and HIT / MISS / SKIP: they come from `experimental.requestInsights`, which only `next dev` emits |
| Server Actions with their names (read from the build's manifests), status, time, revalidation and redirects | **Server render time and the span profiler**: also request insights. The profiler falls back to the page visits the browser recorded |
| Revalidate by tag or path | **Exact route pattern**: rebuilt from the URL and `useParams()` instead |
| SEO, broken links, client errors, security check | The **HMR socket** row in the info panel reads `none (production build)` |

### How the access check works

- Without the variable, or with one shorter than 16 characters, production behaves exactly as described in [Production](#production).
- On every page load, `<NextToolbar>` looks for a `next-toolbar` cookie. Without it, it does nothing: no request, no toolbar code downloaded. Your visitors never pay for the toolbar.
- With the cookie, it calls the server route once. The server compares the cookie with the secret in constant time and answers 200 or 404. Only on 200 does the browser download the toolbar's chunk.
- The server route checks the secret on **every** `GET` and `POST`, so the revalidate buttons can't be used without it either. A wrong cookie gets the same 404 as none.

### Turn it off

- For one browser: delete the cookie, `document.cookie = 'next-toolbar=; path=/; max-age=0'`, and reload.
- For everyone: remove `NEXT_TOOLBAR_SECRET` from the server and restart it. Rotate the value whenever someone who knew it leaves the team.
- Treat the secret like a password: never put it in a `NEXT_PUBLIC_` variable (that ships it to every browser), a URL or the repository.

### Limits

- **Self-hosted only.** The cached-fetch list reads `.next/cache/fetch-cache` from the server's disk, so it needs one `next start` process with Next's default cache. On Vercel, other serverless platforms or with a custom `cacheHandler` (Redis…), the list is empty or partial; the rest of the toolbar still works.
- The route reads the manifests and the cache from `.next` in the directory `next start` runs in. With a custom `distDir`, action names and cached fetches won't be found.
- If a `middleware`/`proxy` guards `/api`, let `/api/next-toolbar` through on staging too.

Not showing up? See [Troubleshooting](./troubleshooting#the-toolbar-doesnt-show-on-a-staging-server).
