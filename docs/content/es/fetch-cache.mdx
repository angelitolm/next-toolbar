Con las request insights activadas, NextToolbar muestra cada `fetch` que hicieron tus server components y qué hizo con él la **caché de datos** de Next.

## Resultados

Estos son los valores que Next registra internamente (`next/dist/server/lib/patch-fetch.js`):

| Resultado | Significado |
|---|---|
| **HIT** | Servido desde la caché de datos. |
| **HMR** | Solo en desarrollo: reutilizado a través de una recarga en caliente para que editar código no vuelva a pedirlo todo. |
| **MISS** | Cacheable; se pidió al origen y se guardó. |
| **SKIP** | No cacheable: `no-store`, `revalidate: 0`, una recarga forzada… |
| **?** | Sin información de caché: el fetch falló, o la versión de Next no la reporta. |

## Porcentaje de acierto

```
hit rate = (HIT + HMR) / (HIT + HMR + MISS)
```

`SKIP` y los fetches desconocidos quedan fuera: nunca se pretendió que se guardaran en caché, así que no deberían bajar el porcentaje. Si nada era cacheable, no se muestra ningún porcentaje.

## Motivos de caché

Next adjunta un motivo a cada resultado. El profiler lo muestra junto a la píldora:

| Motivo | Qué lo causó |
|---|---|
| `revalidate: never` | `cache: 'force-cache'` (Next lo guarda como un revalidate "infinito", 4294967294 s) |
| `revalidate: 30` | `next: { revalidate: 30 }` o el `revalidate` del segmento |
| `cache: no-store` / `cache: no-cache` | Las opciones del fetch |
| `fetchCache = …` | La configuración `fetchCache` del segmento |
| `noStore call` | Se llamó a `noStore()` antes del fetch |
| `auto cache` / `auto no cache` | Sin opción explícita: decidió Next (p. ej. `POST` o cabeceras de autenticación → sin caché) |
| `cache-control: no-cache (hard refresh)` | El navegador hizo una recarga forzada; Next se saltó la caché a propósito |

## Dónde lo ves

- **Barra**: `fetch 3 · 67% hit` para la página actual.
- **Panel de fetch** (al pasar el ratón): chips de resultado (`HIT 2 · SKIP 1`) y cada fetch con su resultado, tiempo, tags y frescura.
- **Profiler**: una tabla por petición con resultado y motivo, y los totales de cada petición capturada en la cabecera.

## Tags y revalidación

Piensa en las devtools de react-query, pero en el servidor: el **tag** de un fetch es su query key, su `revalidate` es el stale time, y revalidar un tag es `invalidateQueries`.

```tsx
fetch(`${api}/products`, { next: { tags: ['products'], revalidate: 60 } })
```

Con la [ruta de servidor](./server-actions) montada, el panel de fetch muestra para cada fetch:

- **Frescura**: `fresh · stale in 45s`, `stale for 12s`, o `cached, no expiry` para `force-cache`.
- **Sus tags**, y un botón <kbd>↻</kbd> que ejecuta `revalidateTag(tag, { expire: 0 })` con ellos y refresca la página. Solo se vuelven a pedir los fetches con ese tag; el resto sigue en caché.
- **Response headers** (plegados), de la respuesta en caché; los valores de `set-cookie` se ocultan. Los headers y el body del propio request no se muestran: la caché de Next no los guarda, solo un hash de ellos como clave de caché.
- **This page** abajo: `revalidatePath` de la ruta actual, para los fetches sin tags.

Para revalidar un tag que no está en la página actual, escríbelo en el [panel de Server Actions](./server-actions).

Pruébalo: la lista de abajo hace de página y la barra al pie de la pantalla muestra sus fetches.

  Las request insights no traen los tags, así que la ruta de servidor los lee de la caché de datos de Next en disco (`.next/dev/cache/fetch-cache`) y la barra los cruza con los fetches de la página por URL. Los fetches con `cache: 'no-store'` nunca se guardan y no tienen tags. `'use cache'` con `cacheTag` vive en memoria y no se muestra.

## En un servidor de staging

En una build de producción con [acceso de staging](./configuration#staging-qa-self-hosted) no hay request insights, así que la barra no puede saber qué fetches hizo esta petición. El segmento pasa a ser **cached fetches**: todas las entradas de la caché de datos de Next (`.next/cache/fetch-cache`), de la más reciente a la más antigua, de toda la app, no solo de la página actual.

Cada fila muestra:

- La URL y el status HTTP de la respuesta en caché (el método no se guarda; Next solo cachea `GET` salvo que se fuerce).
- **Frescura**: `fresh · stale in 45s`, `stale for 12s`, o `cached, no expiry`.
- **Tags**, con el botón <kbd>↻</kbd> para revalidarlos, y **Response headers** (plegados, `set-cookie` oculto).

Lo que no puede mostrar: el tiempo, HIT / MISS / SKIP y el motivo de caché, que solo vienen de los request insights. Los fetches con `cache: 'no-store'` nunca se guardan, así que nunca aparecen. La lista se lee al cargar la página y cada vez que abres el segmento; tras revalidar, la entrada nueva aparece cuando una página vuelve a leer ese fetch.

## Un ejemplo práctico

El playground tiene una página `/cache` con tres fetches a una API local:

```tsx
fetch(`${api}?forced`, { cache: 'force-cache' })
fetch(`${api}?revalidated`, { next: { revalidate: 30 } })
fetch(`${api}?fresh`, { cache: 'no-store' })
```

| Carga | forced | revalidated | fresh | Porcentaje |
|---|---|---|---|---|
| Recarga forzada (<kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>R</kbd>) | SKIP (hard refresh) | SKIP (hard refresh) | SKIP (no-store) | — |
| Navegación en el cliente | HIT (never) | HIT (30) | SKIP (no-store) | 100% |
| Tras editar un archivo | HMR | HMR | SKIP | 100% |

<Callout type="tip">
  El fetch `no-store` es también la razón por la que esta página muestra **Dynamic** aunque los datos de desarrollo de Next digan estática. Consulta [Modo de render](./render-mode#fetches-no-store).
</Callout>
