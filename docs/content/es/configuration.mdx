NextToolbar no necesita configuración para funcionar. Esta página enumera lo que *puedes* configurar, en el componente y en `next.config`.

## Props

```tsx
<NextToolbar theme="system" />
```

| Prop | Tipo | Por defecto | Descripción |
|---|---|---|---|
| `theme` | `'system' \| 'light' \| 'dark'` | `'system'` | Tema inicial. `system` sigue la preferencia del sistema operativo. El botón de tema de la barra lo sobrescribe y recuerda la elección por navegador. |
| `securityCheck` | `boolean` | `true` | Comprueba tu versión de Next.js contra los avisos de seguridad de GitHub. Consulta [Seguridad](./security). |

El paquete también exporta los tipos `NextToolbarProps` y `Theme`.

## Opciones de `next.config`

| Opción | Recomendado | Por qué |
|---|---|---|
| `experimental.requestInsights` | `true` (Next 16.3+) | Activa los tiempos del servidor, los fetches con su resultado de caché, los errores del servidor, los patrones de ruta exactos, la corrección del modo de render por no-store y el profiler. |
| `devIndicators` | `{ position: 'top-right' }` o `false` | El indicador de Next está abajo a la izquierda por defecto, encima del logo de la barra. |

```ts title="next.config.ts"
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  devIndicators: { position: 'top-right' },
  experimental: { requestInsights: true },
}

export default nextConfig
```

<Callout type="note">
  `requestInsights` solo existe desde Next 16.3. En versiones anteriores TypeScript lo marca como opción desconocida en `next.config.ts`, así que añádelo solo en 16.3+.
</Callout>

## `basePath` y `assetPrefix`

Ambos funcionan sin configuración adicional:

- La barra encuentra el socket del servidor de desarrollo igual que lo hace el propio cliente de Next: a partir de la ruta de los scripts de Next (todo lo que hay antes de `/_next/`). Eso cubre `basePath`, y `assetPrefix` incluida una URL de CDN.
- Next escribe `basePath` en el código de la barra en tiempo de build (`process.env.__NEXT_ROUTER_BASEPATH`), para que pueda hacer coincidir las URLs que lo incluyen (`/docs/blog/hello`) con las rutas que Next reporta sin él (`/blog/hello`).

## Preferencias guardadas

La barra guarda dos pequeñas preferencias en el `localStorage` del navegador, por origen:

| Clave | Valores | La establece |
|---|---|---|
| `next-toolbar:collapsed` | `'1'` o `'0'` | Minimizar / expandir la barra |
| `next-toolbar:seen` | Lista JSON de nombres de segmentos | Abrir un segmento que tiene la etiqueta **new** |
| `next-toolbar:theme` | `'system'`, `'light'`, `'dark'` | El botón de tema |

Bórralas para volver a los valores por defecto. Si `localStorage` no está disponible (modo privado, almacenamiento bloqueado), la barra sigue funcionando y simplemente no recuerda nada.

## Ruta de servidor

Opcional. `@angelitolm/next-toolbar/server` exporta dos route handlers; móntalos en `/api/next-toolbar`:

```ts title="app/api/next-toolbar/route.ts"
export { GET, POST } from '@angelitolm/next-toolbar/server'
```

| Método | Hace |
|---|---|
| `GET` | Devuelve los nombres de las Server Actions, leídos de los archivos `server-reference-manifest.json` de Next en `.next`. |
| `POST` | Ejecuta `revalidatePath` o `revalidateTag` con lo que envía la barra. |

- Los dos responden **404 fuera de `next dev`**, así que desplegar el archivo no tiene riesgo (salvo que lo [actives en un servidor de staging](#staging-qa-self-hosted)).
- También responden 404 si la petición no lleva la cabecera `x-next-toolbar`. Los navegadores solo mandan una cabecera propia a otro origen después de una petición CORS previa, que esta ruta nunca aprueba, así que otra web abierta en tu navegador no puede llamarla.
- La ruta es fija. Si un `middleware`/`proxy` protege `/api`, deja pasar `/api/next-toolbar` en desarrollo.
- Lee los manifests de `.next` en el directorio donde se ejecuta `next dev`: con un `distDir` propio no encontrará los nombres de las actions (revalidar sigue funcionando).

## Error boundary

No es una opción de la barra, pero vale la pena repetirlo: añade `app/error.tsx` para que un error de render no tumbe el layout raíz, y la barra con él. Consulta [Empezar](./getting-started#4-mantenla-en-pantalla-cuando-una-página-falla).

## Componente de demo

`NextToolbarDemo` dibuja la misma barra a partir de los datos que le pases, en cualquier entorno, producción incluida. Es lo que usa la [demo en vivo](./demo); úsalo para documentación, capturas o presentaciones, no en tu app.

```tsx title="app/showcase/page.tsx"
'use client'
import { NextToolbarDemo } from '@angelitolm/next-toolbar/demo'

export default function Showcase() {
  return <NextToolbarDemo pathname="/blog/hello" params={{ slug: 'hello' }} status={200} timingMs={42} isStatic />
}
```

| Prop | Descripción |
|---|---|
| `pathname`, `params` | La página simulada |
| `status`, `timingMs`, `via` | Status HTTP y TTFB (`'document'`) o tiempo de navegación (`'rsc'`) |
| `isStatic` | Lo que dicen los datos de dev de Next: `true`, `false`, u omitido para "Rendering…" |
| `insights` | Request insights simulados (se exportan los tipos `Insight`, `InsightFetch`, `InsightSpan`) |
| `clientErrors` | Errores de cliente con `message` y `stack` opcional |
| `nextVersion`, `theme` | Por defecto: `'16.3.6'` y `'system'` |

## Producción

No hay nada que desactivar. En una build de producción la barra renderiza `null`, no hace peticiones y no abre conexiones. Su código va en un chunk aparte que las páginas nunca cargan para tus visitantes.

## Staging (QA self-hosted)

NextToolbar es una herramienta de desarrollo. **No debe estar en un entorno de producción**, y nada en el paquete la activa ahí por sí solo.

Un servidor de staging para pruebas específicas de QA es la única excepción, y es **una decisión deliberada de vuestro equipo de desarrollo**: la barra sigue apagada hasta que alguien define el secreto de abajo en ese servidor. Hazlo solo en staging, solo mientras QA lo necesite, y nunca en el entorno al que llegan tus usuarios.

<Callout type="warning" title="Nunca en producción">
  No definas `NEXT_TOOLBAR_SECRET` en producción, ni siquiera temporalmente para depurar. Con la ruta de servidor montada, quien tenga el secreto puede listar tus Server Actions y revalidar tu caché.
</Callout>

Para activarla en un servidor de staging propio (`next build` + `next start`):

1. Monta la [ruta de servidor](#ruta-de-servidor): es la que decide quién entra.
2. Define en el servidor un secreto de al menos 16 caracteres:

   ```bash
   NEXT_TOOLBAR_SECRET=una-cadena-larga-y-aleatoria
   ```

3. En el navegador que deba ver la barra, guárdalo en la cookie `next-toolbar` (una vez, desde la consola de DevTools):

   ```js
   document.cookie = 'next-toolbar=una-cadena-larga-y-aleatoria; path=/; max-age=2592000; samesite=strict'
   ```

- Sin la variable, o con una de menos de 16 caracteres, producción se comporta exactamente como arriba.
- Solo un navegador con la cookie `next-toolbar` pregunta a la ruta de servidor; el servidor la compara con el secreto en tiempo constante. Una cookie incorrecta recibe el mismo 404 que ninguna.
- En una build de producción no hay servidor de desarrollo de Next, así que **no hay render mode, ni request insights, ni socket HMR**. Lo que funciona: status HTTP, TTFB y tiempo de navegación, SEO, enlaces rotos, Server Actions (con sus nombres, sacados de los manifests de la build), revalidación, errores de cliente y el chequeo de seguridad.
- Trata el secreto como una contraseña: nunca uses una variable `NEXT_PUBLIC_` para él, y cámbialo cuando alguien deje el equipo.
